# AGENTS.md: docs

VitePress documentation site. Per-package docs live in `docs/<name>/` and follow the Diátaxis framework (structure: `.agents/reference/docs-template.md`; procedure: the `document` skill, `.agents/skills/document/SKILL.md`). Also hosts the interactive REPL (`docs/repl.md`) and the custom theme under `docs/.vitepress/`.

## Local contracts

- Each `docs/<name>/` has the four standard pages: `index.md` (Explanation), `usage.md` (How-to), `api.md` (Reference), `examples.md` + `examples/*.md` (How-to). Follow `.agents/reference/docs-template.md` for required frontmatter and section order.
- Each `docs/<name>/` also carries `migration.md`: the breaking-change contract for a CalVer train (one section per break, old code → new code; see `RELEASE.md`). `new-package.mjs` scaffolds it empty; a breaking change fills it in the same commit as the change file.
- REPL wiring lives in `docs/.vitepress/theme/components/repl/`:
  - `examples/<name>/`: hand-authored example modules (the only content authors write by hand), registered in the matching `index.ts` **and** in the top-level `examples/index.ts` map. `__tests__/replExamples.test.ts` fails when a folder is unregistered or a REPL-eligible package has no examples at all.
  - `execution/`: the sandbox execution engine (Monaco loading + TS transpile, `@vielzeug/sandbox`-based iframe execution, import rewriting, output formatting). Pure logic here is unit-tested under `execution/__tests__/`.
  - `registry.generated.ts`: **gitignored, generated by `bun run gen:repl-registry`** (`scripts/generate-repl-registry.ts`) from each package's build output. Never hand-edit; regenerate instead.
- **DOM-output packages (`ore`, `refine`, `prism`) render into the REPL's Preview pane**: the execution sandbox iframe is visible there, themed with the site's dark mode, and sized from the iframe's reported content height. Examples for these packages mount into `document.body` (the iframe's body) and emit `repl:dom` automatically; keep them registered like any other package. `REPL_EXCLUDED_PACKAGES` in `scripts/vielzeug-packages.ts` is empty: every package under `packages/` that is browser-resolvable (`listVielzeugPackages`; only `codex` is not) must ship an IIFE bundle (`vite.bundle.config.ts` + `build:bundle` in its build chain) and REPL examples — `replExamples.test.ts` gates the examples, the registry generator fails on a missing bundle.
- `@vielzeug/*` alias maps used by `docs/.vitepress/config.ts` and `scripts/vitest.repl.config.ts` are both derived from the `packages/` directory listing (`scripts/vielzeug-packages.ts`): don't hand-maintain either list.
- Navbar and homepage package listings come from `docs/.vitepress/theme/components/packageGroups.ts` (one `{ id, tagline }` entry per package, in exactly one group). `PACKAGE_GROUPS` drives both the Packages navbar menu (`PackagesMenu.vue`) and the homepage grid/hero rotation (`HomePage.vue`). A new package is invisible on the site until it is added there; `__tests__/packageGroups.test.ts` fails until every `packages/<dir>` slug appears exactly once, so `bun run test` is the gate.
- Keep docs in sync with `packages/<name>/src/index.ts`; the `codex` package bundles these docs, so changes here feed the MCP server.
- Editing docs invalidates the `codex` bundle: rebuild Codex before VitePress (`bun run --filter @vielzeug/codex build`, then `bun run docs:build`). Codex refreshes bundled MCP data and `llms*.txt`; VitePress copies those current files into site output.

## Verification

- Structure and relative links: `bun run validate:docs -- --package=<name>`.
- Navbar/homepage coverage: `bun x vitest run docs/.vitepress/theme/components/__tests__/packageGroups.test.ts` (also runs in `bun run test`); fails when a package is missing from or duplicated in `packageGroups.ts`.
- REPL example coverage: `bun x vitest run docs/.vitepress/theme/components/__tests__/replExamples.test.ts` (also runs in `bun run test`); fails when an `examples/<name>/` folder is not registered in `examples/index.ts` or a REPL-eligible package ships no examples.
- Sidebar coverage: `bun run validate:sidebar -- --package=<name>`. The hand-authored `themeConfig.sidebar` in `docs/.vitepress/config.ts` drifts both ways (links outlive their pages, new pages never get linked) and `ignoreDeadLinks` means the build never complains, so this is the only gate. It imports the real config (generated Refine links included), so text-parsing the sidebar is never the check.
- Build: `bun run docs:build` (renders VitePress; dead links are not a build gate while `ignoreDeadLinks` is enabled).
- Local preview: `bun run docs:dev`.
