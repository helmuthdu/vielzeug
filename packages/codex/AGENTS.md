# AGENTS.md: codex

MCP (Model Context Protocol) server and CLI that exposes all Vielzeug docs to AI clients. An executable tool, not a consumed library; standalone: no `@vielzeug/*` runtime dependencies. The docs it bundles live in `docs/` (see `docs/AGENTS.md`).

## Local contracts

- **Build bundles the docs.** `prepare:data` (`scripts/generate-bundled-data.ts`) reads `docs/` and generates `packages/codex/data/` before compilation. It runs as the first step of `build` and `test:integration` (explicit, not an npm `pre*` hook: lifecycle hooks are runner-dependent): do not call `tsc` directly when you need fresh data.
- `packages/codex/data/` is **generated and gitignored**: never hand-edit or commit it. `prepare:data` requires `packages/refine/dist/custom-elements.json` and fails without it; `@vielzeug/refine` is a workspace devDependency purely so `bun run build` builds it first.
- **Snapshot layout is code, data is data.** A snapshot is one flat directory: `manifest.json` (`{schemaVersion, version}` only — filenames are loader constants), `catalog.json`, lazy `packages/<slug>.json` content chunks, optional `refine.json`, and the `llms.txt` pair. There is no search index: `Catalog.search()` reads content chunks through the same cache as the content getters. `loadSnapshot(directory)` takes the directory directly; dev (`scripts/dev.ts`) and release (`prepare:data`) both publish it through one staging swap.
- Entry points: `src/cli.ts` (CLI, run locally as `bun dist/cli.js`; the published `codex` bin keeps its `#!/usr/bin/env node` shebang for consumers), `src/index.ts` (the single public entry: catalog, snapshot loader, stdio transport, errors, MCP server factory, and HTTP host), `src/catalog.ts` (semantic catalog reads including Refine component lookup), `src/server.ts` (`createMcpServer`), `src/http.ts` (loopback Streamable HTTP transport), `src/snapshot.ts` (validated snapshot loader), and `src/skills.ts` (CLI-only `codex skills install`: not exported from any entry point).
- **`skills/vielzeug/SKILL.md` is the consumer-facing agent skill** shipped in the npm package (`files`) and installed into downstream projects via `codex skills install`. `.agents/skills/vielzeug` at the repo root is a symlink to it, so demos and monorepo agents load the same file. Its `<!-- GENERATED:skill-packages -->` block is rendered from `packages/*/package.json` by `bun run gen:ai-data` (guarded by `bun run check:ai-data`): edit the prose, never the block. It must not hand-list Refine components or tokens; it points agents at the `refine-*` MCP tools and `dist/custom-elements.json` instead.
- **MCP tools live in `src/tools/`, one file per domain**: `packages.ts` (generic catalog operations), `refine.ts` (Refine-only tools, prefixed `refine-*`; `createMcpServer` adds them only when the snapshot carries Refine metadata, so tools that could only answer "unavailable" are never offered), `index.ts` (MCP adapter: the only place that serializes MCP results; tools return domain values), `schema.ts` (local `ToolSchema` declarations: the single source for both wire `inputSchema` and runtime validation via `parseArgs()`), and `shared.ts` (MCP manifest shape).
- **MCP tool tables are generated, not hand-written.** `bun run gen:tool-docs` (`scripts/generate-tool-docs.ts`, run explicitly after `build`: deliberately not part of `build`, which must not write outside the package) renders the `<!-- TOOLS:GENERIC -->` / `<!-- TOOLS:REFINE -->` tables in `docs/codex/tools.md` straight from `packageTools` and `refineTools`: never edit those tables by hand, edit the tool's `description`/`inputSchema` and run the generator. This script reads compiled `dist/tools/packages.js` and `dist/tools/refine.js` (not `src/`) because `src/tools/*.ts` import their siblings with `.js` specifiers for the real NodeNext build, so resolving them against `src/` would read the wrong files: run `bun run build` first if you need fresh tables.
- **Expected catalog failures throw `CatalogError(code, message)`, never hand-built MCP error results.** `code` is `'INVALID_ARG' | 'NOT_FOUND' | 'UNAVAILABLE'`; `registerTools()` centrally maps it to MCP `{isError: true}` JSON. Resolve package, content, and Refine data through `Catalog` methods instead of duplicate lookups in tools.
- **No hand-duplicated package internals.** Don't hand-author reference data that mirrors another package's real exports (e.g. a curated list of another package's functions/types): it drifts silently. If a tool needs that information, derive it from the already-bundled `apiSource`/`docs`/`typeSignatures` (see `get-type-signature`, `get-docs`) or from real generated build output (see refine's Custom Elements Manifest in `readRefineComponents` / REPL examples in `scripts/repl-examples.ts` / exported-symbol text in `scripts/type-signatures.ts`), not from a second, hand-maintained copy.
- Scripts stderr output must go through `scripts/_log.ts` (`log()`). Never use bare `process.stderr.write` in scripts.
- After changing docs in `docs/`, rebuild to refresh the bundle: `bun run --filter @vielzeug/codex build`.
- **codex has no `@vielzeug/*` dependency edge, so it never rides a train for someone else's pin**: full-family trains still publish it (alignment-only when it has no change file), but its changelog entry is empty unless it carries its own change file. It bundles all of `docs/` into its published `data/` dir at build time, so a docs-only change still changes codex's shipped npm content and needs its own change file to say so. A pre-commit hook (`scripts/auto-change-codex.mjs`, wired in `lefthook.yml` as `change:codex`, glob `docs/**`) auto-writes a patch change file for codex whenever docs change and none is already pending: don't hand-write a duplicate one.

## Testing

- Tests are split into two Vitest projects (`vitest.config.ts`): `*.test.ts` uses temporary fixture snapshots only; `*.integration.test.ts` regenerates a current snapshot from real `docs/` and sibling packages, requiring a full monorepo checkout.
- `bun run test:unit`: fast loop while iterating, no `prepare:data` needed beforehand.
- `bun run test:integration` / `bun run test`: integration coverage; `test:integration` regenerates snapshot data first.
- `generator.integration.test.ts` validates real monorepo snapshot generation. New tests that load real package/docs inputs belong in `*.integration.test.ts`; all other tests must construct temporary snapshots.

## Adding an MCP tool

Add it to `src/tools/packages.ts` (generic) or `src/tools/refine.ts` (Refine-specific: use a `refine-` name prefix), define its local `ToolSchema` once with `satisfies ToolSchema`, return a domain value from `execute()`, use `Catalog` methods for expected failures, cover it in `src/__tests__/`, then run `bun run build` and `bun run gen:tool-docs` to refresh the generated tool reference.

## Verification

- Tests (`test:integration` runs `prepare:data` first): `bun run --filter @vielzeug/codex test`
- Fast unit-only loop: `bun run --filter @vielzeug/codex test:unit`
- Lint: `bun run --filter @vielzeug/codex lint`
- Build: `bun run --filter @vielzeug/codex build`; then `bun run --filter @vielzeug/codex gen:tool-docs` when tool descriptions or schemas changed
