# AGENTS.md: scripts

Repo tooling: release/publish automation, git worktree helper, generated-doc sync, and REPL
codegen/validation. Not a published package: consumed by `bun` scripts, CI workflows, and
directly via `bun scripts/...` (both `.mjs` and `.ts`: Bun runs plain JS and TypeScript natively).

## Layout

| Path                        | Purpose                                                                                                                                                                                                                                                                                                     |

| `lib/cli.mjs`               | Shared primitives every script here needs: `isMain()`, `run()` (subprocess exec with three IO postures: capture/inherit/quiet), `parseArgs()` (positionals + `--flag=value`/bare-boolean flags, no space-separated form: see its own header comment for why). Paired with a hand-written `lib/cli.d.mts`. |
| `lib/marker-sync.mjs`       | Generic idempotent generated-file writer with a `--check` mode for CI. Used by generators such as `sync-ai-data.mjs`. |
| `lib/packages.mjs`          | The one real `packages/*/package.json` scan: `readPackageManifests()`. `sync-ai-data.mjs`, `worktree.mjs`, and `vielzeug-packages.ts` derive their own views from it. Paired with a hand-written `lib/packages.d.mts`. |
| `lib/validator.ts`          | Shared harness for the diagnostic validators (`validate-docs.ts`, `validate-readme.ts`, `validate-sidebar.ts`): `runValidator()` owns argv parsing, the strict `--package=` filter (`resolvePackageFilter()`), the `[rule] file:line: message` + hint reporting, the summary lines, and the exit code; a validator contributes only its rules and a label. | `repl-metadata.ts`          | Curated REPL display content (per-package descriptions, arsenal's function categories) that can't be derived from source: kept separate from the AST-manipulation logic in `generate-repl-registry.ts` so editing a description is a one-line content change.                                              |
| `validate-repl.ts`          | Extracts every REPL example's `code`, writes it as a runnable temp file, and executes it via `vitest` (`vitest.repl.config.ts`) as a real test.                                                                                                                                                             |
| `validate-docs.ts`          | Structural package-doc validator: explicit contracts, complete package/docs inventory, recipe-index parity, and relative Markdown links. It reports stable diagnostics (via `lib/validator.ts`) but does not judge prose or API semantics.                                                                                               |
| `validate-readme.ts`        | Structural package README validator: enforces the canonical README shape (title, blockquote description, Installation, Quick Start, optional Features, Documentation, License) defined in `.agents/reference/readme-template.md`. Reports stable diagnostics, does not judge prose.                                   |
| `validate-sidebar.ts`       | Sidebar/page parity validator: every internal `themeConfig.sidebar` link resolves to a page on disk, and every page of a `standard`-contract package is reachable from its sidebar (catalog/component-library exempt, per `DOCS_CONTRACT_OVERRIDES`). Reads the sidebar by importing the real config under Bun (which runs the `.ts` config natively), never by parsing its text: part of it is generated (`refineComponentSidebarGroups`), so a text scan would flag every generated Refine link. |
| `verify-prod-gate.mjs`      | Repo-wide assertion that no published artifact contains a raw `__<PKG>_PROD__` reference (dev-warn gate compiled out). Runs in CI (`ci.yml`, after a full `bun run build`); locally via `bun run verify:prod-gate`. |
| `verify-packed-packages.mjs` | Creates release-shaped tarballs, installs their workspace dependency closure and external optional peers into an isolated fixture, and validates packed metadata, ESM/CJS exports, and TypeScript resolution. Release preparation calls it after a train is applied; locally run `bun run verify:packed -- --package=@vielzeug/<name>` or `--package=all`. |

There is deliberately no `cli.mjs` discovery/router entrypoint. `bun run` (no args) already lists every command below by name straight from `package.json`: a second, hand-maintained routing table over the same information would be pure duplication with strictly worse ergonomics (an extra subprocess hop, and a table that can silently point at a renamed file with nothing to catch it).

## Local contracts

- **Two file kinds, one runtime.** Bun is the single configured runtime: root scripts, CI (`setup-bun`), and git hooks all invoke `bun`. `.mjs` files are plain JavaScript, so `bun scripts/<file>.mjs` runs them with no loader (their `#!/usr/bin/env node` shebang is only a fallback for a direct `./scripts/<file>.mjs` call, which nothing in the repo makes). `.ts` files (`generate-repl-registry.ts`, `validate-repl.ts`, `vielzeug-packages.ts`, `repl-metadata.ts`, the `vitest.*.config.ts` files) are docs/REPL tooling, run via `bun scripts/<file>.ts` (Bun executes TypeScript natively; see their `bun` script wiring): they need the TS compiler API and real project types, which a plain-JS script doesn't. Don't mix: a `.ts` file importing a plain `.mjs` module needs a hand-written `.d.mts` sibling (see `lib/cli.d.mts`, `lib/packages.d.mts`) since `tsc` can't infer types across that boundary on its own: `validate-repl.ts` and `vielzeug-packages.ts` do this because they use real, nontrivial logic from `lib/cli.mjs`/`lib/packages.mjs`; `generate-repl-registry.ts` deliberately does _not_ import `lib/cli.mjs` just for its one-line `isMain` check (see that file's own header): a cross-language type contract isn't worth paying for a single three-token check. There's no automated check that a `.d.mts` and its `.mjs` stay in sync for the imports that do exist: a deliberate bet, given how small each of these modules' surfaces are; update both in the same commit.
- **Every script follows the same "pure functions + guarded entry point" shape**: importing any script here for a test must never touch the filesystem, network, or spawn a process on its own. Side effects (reading real files, writing generated output, spawning `git`/`npm`/`gh`) live behind an `isMain` check at the bottom (`if (isMain(import.meta.url)) { ... }`, imported from `lib/cli.mjs`, or inlined as `process.argv[1] === fileURLToPath(import.meta.url)` for a `.ts` file with no other reason to import that module), exactly like every test file's own "module has no import-time side effects" smoke test asserts.
- **A shared full-repo scan warns and skips on a bad input, it does not throw.** `lib/packages.mjs`'s `readPackageManifests()` is on the VitePress dev-server startup path (via `vielzeug-packages.ts`, loaded by `docs/.vitepress/config.ts` on every `bun run docs:dev`/`docs:build`) as well as `sync-ai-data.mjs`'s and `worktree.mjs`'s full-repo scans: all run across _every_ package, not just the one a caller cares about. One contributor's mid-edit syntax error in an unrelated `package.json` must not be able to take down everyone else's dev server; `readPackageManifests()` logs a clear `console.error` and skips that one package instead of throwing. A caller that needs to fail loudly on one _specific_ named package's bad JSON already does: `worktree.mjs`'s `cmdAdd()` throws "No such package" for a slug this function silently (but audibly) skipped.
- **Every `isMain()` catch prints the full error, never just `.message`**: several scripts wrap a lower-level failure in `new Error(msg, { cause })` (a failed `git worktree add`, a corrupted marker file); `console.error(err)` renders the whole cause chain, `console.error(err.message)` silently throws that context away right where a human is trying to debug it. Use `process.exitCode = 1`, not `process.exit(1)`: let the process exit naturally instead of cutting off any in-flight stdout/stderr write.
- **Read `process.env.*` flags (`DRY_RUN`, etc.) inside the function that uses them, never at module top level.** A module-level `const dryRun = process.env.DRY_RUN === '1'` freezes the value at import time: invisible and surprising for anything that sets the env var after the module is already loaded (a test, most commonly).
- **Prefer `createRequire(import.meta.url).resolve(...)` over `import.meta.resolve`** when a script needs real Node module resolution (see `validate-repl.ts`'s `resolveVitestBin()`): the two runtimes resolve bare specifiers from a `.ts` entry differently, and `require.resolve` is the shape both agree on.
- **`run()`'s three IO postures** (`lib/cli.mjs`): default (capture stdout, for parsing output or when failure detail matters: e.g. npm E409 retry), `inherit: true` (share this process's terminal: required for anything interactive: an npm 2FA prompt, a browser-trust flow, or where a human should see git/gh/bun output live), `quiet: true` (discard stdio: for an exit-code-only probe like "does this git tag exist" where even the command's own expected-failure output would be noise).
- **`parseArgs()` never supports a space-separated `--flag value` form**: only `--flag=value` or a bare boolean `--flag`. A space-separated value is ambiguous the moment a positional can also follow (`--interactive packages/ore`: is `packages/ore` the flag's value or the next positional?); one unambiguous rule beats a heuristic that's right most of the time. Every flag in every script here uses `=`.

## Adding or extending scripts

- New shared behavior (a third IO posture, a new arg-parsing case) belongs in `lib/cli.mjs`/`lib/marker-sync.mjs`/`lib/packages.mjs`/`lib/change-files.mjs`, not copy-pasted into the script that first needed it.
- New diagnostic validator: build on `lib/validator.ts`'s `runValidator()` + `Diagnostic`/`ValidationResult`, don't re-implement argv parsing, `--package=` filtering, or diagnostic printing.
- New codegen script with a `--check` mode: build on `lib/marker-sync.mjs`'s `syncFile` + `replaceBetweenMarkers`, don't reimplement the write-vs-check branching.
- New tool that needs "what packages exist / how do they depend on each other": build on `lib/packages.mjs`'s `readPackageManifests()`, don't re-scan `packages/*/package.json` by hand.
- Adding a new top-level tool: give it the same shape as its neighbors (pure functions + `isMain()` guard), add a `bun` script for it in the root `package.json`, add it to this file's Layout table, and write `scripts/__tests__/<name>.test.ts(x)` alongside it.

## Verification

- Tests: `bun x vitest run scripts` (one vitest project: `vitest.config.ts`'s `projects` array includes `scripts/vitest.config.ts`).
- AI metadata drift: `bun run check:ai-data`: a stale `.agents/reference/packages.md` or a dangling `.agents/...` cross-reference anywhere in the repo fail this without writing anything.
- Lint: not linted (`scripts/` is Biome-ignored): correctness here is enforced by tests and by the scripts actually running in CI.
- Smoke-test any script directly: `bun scripts/<file>.mjs` / `bun scripts/<file>.ts`.
